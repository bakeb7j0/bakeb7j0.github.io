The Federated ALM Manifesto

The ALM is not a tool. It is the set of treaties between tools.

Lifecycle management that respects the tools, the teams, and the work — and refuses the centralisation that has failed the category for forty years.

Brian Baker · 2026

The problem we refuse to repeat

For decades, the ALM industry has operated under a false assumption: that one tool must own the lifecycle. Every major platform — Jira, Polarion, DOORS, Azure DevOps — positions itself as the hub through which all work must flow. The result is predictable and universal:

  • Teams put some data in the ALM, but do their real work elsewhere.
  • The gap between the ALM and reality is bridged by manual sync, semi-automated duct tape, and hope.
  • Data in any single system becomes untrustworthy.
  • The tool that was supposed to create clarity becomes the primary source of confusion.

We have seen this firsthand. Requirements in Jama. “Management” in Jira. Actual engineering in GitLab. Three systems, three incomplete pictures, zero source of truth. Every organisation that adopts a centralised ALM eventually arrives at this same place — not because the people failed, but because the model is wrong.

The false equivalence

The centralised ALM model rests on a seductive logical error:

“We refine requirements during sprints, therefore our sprint tool must own requirements.”

This is like saying:

“We discuss architecture in meetings, therefore our calendar app is our architecture tool.”

Just because an activity occurs within a process does not mean the process tool owns that activity’s artifacts. Requirements analysis can absolutely happen inside Scrum ceremonies. That does not make Jira a requirements management system. It makes Jira a place where people talk about requirements — which is a fundamentally different thing.

Dual citizenship

Every work item in a software lifecycle has a home system — the tool where it is authoritative, where its schema is enforced, where its history is canonical. But work items also make guest appearances in other systems. A requirement appears in a sprint board. An epic appears in a traceability matrix. A test result appears in a PM dashboard.

The centralised model says

“Immigrate everything into one country.” The result is bloated tools, half-populated fields, and data that belongs nowhere because it was forced to belong everywhere.

The federated model says: grant dual citizenship. Each work item keeps its home. Other systems recognise it, reference it, and interact with it — but they do not try to own it. A requirement’s home is the requirements tool. An epic’s home is the engineering platform. A test plan’s home is wherever test plans are managed.

Seven principles

1

Each tool owns exactly one domain

A requirements tool manages requirements. An engineering platform manages implementation. A test management system manages test plans. No tool tries to be adequate at everything. Each tool strives to be excellent at one thing.

2

Authority is never duplicated

For any piece of data, exactly one system is the source of truth. Others may hold references or derived views — but when there is a conflict, the home system wins. There is no “sync” between equals, because there are no equals. There is one authority and many consumers.

Note what is deliberately not permitted: a durable copy of another system’s mutable state. A reference addresses an artifact; a copy describes it — and a description begins drifting the moment the home system changes, silently, with no event to tell you. A consumer holding a stale description has not saved a network call, it has manufactured a second authority.

3

Integration is by reference, not by copy

When the requirements tool needs to know an epic’s status, it holds a reference — a project ID and an epic ID — and queries the engineering platform. It does not copy the epic into its own database and try to keep it updated. References are cheap, durable, and never stale. Copies are expensive, fragile, and always eventually wrong.

4

Interfaces are the architecture

The value of a federated ALM is not in any single tool. It is in the contracts between tools — the APIs, webhooks, and data formats that let each tool be a good citizen. An organisation with five excellent tools and no interfaces has a fragmented ALM. The same organisation with well-defined interfaces has a federated one. The difference is not the tools. It is the connective tissue.

5

Views are derived, never stored

A PM dashboard that shows “72% of requirements have passing tests” does not store that number. It computes it on demand by querying the requirements tool and the test system. Stored rollups are lies waiting to happen. Derived views are always current.

6

The lifecycle emerges from composition

No single tool “manages the lifecycle.” The lifecycle is the emergent behaviour of well-composed tools, each doing its job, each respecting the others’ authority. You do not design the lifecycle into a tool. You design the tools to be composable, and the lifecycle reveals itself.

7

Complexity belongs at the boundaries

Individual tools should be simple. The requirements tool does not need to understand sprint velocity. The engineering platform does not need to understand regulatory compliance matrices. Complexity lives in the integration layer — the thin membrane between systems where translation and mapping occur. It is the only place cross-domain knowledge is required, and it should be as thin as possible.

What this means in practice

For requirements management

Build a tool that is ruthlessly focused on requirements — their text, their relationships, their verification status, their traceability. It does not manage sprints. It does not track time. It does not render Gantt charts. It exposes a clean API so that tools which do those things can reference its data.

For engineering

Use the best engineering platform available. Do not try to make it a requirements tool. Let it be excellent at what it is: code, merge requests, CI/CD, epics, issues. When an epic satisfies a requirement, record that link — but the requirement lives elsewhere.

For project management

PM views are dashboards that read from multiple authoritative sources. They are lenses, not ledgers. A PM should never have to “update the status” of something in their tool — the status should flow automatically from the systems where the actual work is happening.

For test management

Test plans are the mirror image of requirements on the verification side of the V-model — but a mirror is not the same room. A test plan’s home is the test management system, exactly as an epic’s home is the engineering platform. Test procedures belong with the code. Test results flow from execution back toward the requirements tool to close the traceability loop — pushed by the systems that produce them, never fetched by reaching through a plan into someone else’s CI.

The V-model’s symmetry is a statement about meaning, not about storage. A requirements tool that absorbed test plans because they “belong with” requirements would have taken a second domain on the strength of a metaphor — which is how every centralised ALM starts.

For compliance

A traceability matrix is not a document you maintain. It is a report you generate on demand from the live state of your federated tools. If your RTM can go stale, your architecture is wrong.

The UNIX precedent

This is not a new idea. It is the oldest idea in software:

Write programs that do one thing and do it well. Write programs to work together.

Doug McIlroy, 1978

The ALM industry ignored this for forty years because there was money in monoliths. We are choosing not to ignore it.

What we are building

Ruthless. Not an ALM platform. Not a project management suite. A tool that does one thing — manages requirements and their traceability to external systems — and does it well.

It will have a clean API. It will integrate with engineering platforms by reference. It will produce audit artifacts on demand. It will be the foundation of a federated ALM, not the totality of one. The rest of the lifecycle will be handled by tools that already exist and already excel at their jobs.

The discipline this imposes on us

Ruthless is the missing citizen, not the missing protocol. It holds up one end of the treaties — requirements and their traceability — and is a good enough citizen that the federation becomes possible around it. But the integration layer is its own component with its own home, not a subsystem of Ruthless.

Principle 1 forbids any tool from owning two domains, and “requirements” and “the protocol between all tools” are unmistakably two. A requirements tool that also owned the connective tissue would be the same centralisation this document rejects, wearing a friendlier name — and it would fail the same way, because the tool that owns the protocol inevitably starts owning the data that flows through it.
