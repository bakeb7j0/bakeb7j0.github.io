Requirements Management — Our Workflow

How we take a customer requirements document and turn it into a traceable, verifiable engineering commitment — and why we do it this way rather than another way.

Eight beliefsFive stagesNine states2026

The workflow is downstream of a small number of beliefs. If you disagree with the beliefs, you will disagree with the workflow — and that is the more useful conversation to have first, which is why they come before the diagram.

01 The beliefs that drive the decisions

Every requirements tool encodes an opinion. Most encode theirs silently, which is how teams end up fighting their tooling without ever being able to name what they are fighting. Ours are written down — each with what it forces us to do and what it costs. A belief with no cost attached is marketing.

B1

Each tool owns exactly one domain

A requirements tool manages requirements. An engineering platform manages implementation. A test management system manages test plans. No tool is asked to be adequate at everything.

ForcesRequirements live in a requirements registry, not in the sprint tool. Epics stay in the engineering platform. Test plans stay in the test system.
CostsMore systems, and a hard dependency on the interfaces between them. There is no single pane of glass you can log into and see everything by clicking around.
B2

Authority is never duplicated

For any piece of data, exactly one system is the source of truth. Others hold references or derived views. When there is a conflict, the home system wins — because there is no conflict to arbitrate, only a stale consumer.

ForcesNo sync jobs, no nightly reconciliation, no “which one is right?” meetings.
CostsYou cannot edit an epic from inside the requirements tool. Round trips are real.
B3

Integration is by reference, never by copy

We store what addresses an artifact — a project ID and an epic ID. We never store what describes it: its status, its title, its assignee. A description begins drifting the moment the home system changes, silently, with no event to tell you.

ForcesEvery status figure is a live query against the system that owns it.
CostsThe requirements tool is only as available as the systems it federates with. Reads are slower than reading a local cache, because there is no local cache.
B4

Views are derived, never stored

A dashboard showing “72% of requirements have passing tests” does not store that number. It computes it on demand. A stored rollup is a lie waiting to happen.

ForcesNo reporting tables, no materialised metrics, no “as of last night.”
CostsA dashboard number is a fan-out across every federated system, every time.
B5 · the expensive one

Missing data is declared, and the operation stops

If a federated system cannot be reached, we say so and abandon what we were about to compute. We do not fall back to a cached figure, do not treat unknown as zero, and do not compute a percentage over “the systems that happened to answer.”

ForcesPartial results are never presented as whole ones. Failures are visible and attributed — “197 of 200 resolved; GitLab unreachable; 3 requirements affected.”
CostsOne unreachable system takes the headline number dark. A programme manager opens the dashboard expecting “68% implemented” and instead sees “unavailable — here is exactly what is missing and why.”

We consider a number that can be quietly wrong to be worse than a number that is honestly absent. We have deliberately not built an “exclude the unavailable and compute anyway” option, even as an opt-in — that is manufacturing the answer with an extra click in front of it.

B6

Satisfaction, Adequacy and Compliance are three different questions

Conflating them under the word “completeness” caused a real design error in our own model, which we corrected. They are now kept apart by construction.

 The questionWho answers
SatisfactionHow far along is this set?The tool — arithmetic over live figures
AdequacyIs this the right set?A human. Never computed, never inferred
ComplianceDoes this requirement have its required sets at all?The tool — a structural check
ForcesThe tool will happily report that a requirement is 100% satisfied by a set of epics that does not actually cover it. It reports arithmetic; it does not certify.
CostsYou cannot automate your way to a defensible requirements baseline. Somebody has to look, and the system records who did.
B7

Judgement is represented, never enforced

We record that a person exercised judgement over a set, and who. We do not refuse to function until they do, do not block queries on unratified sets, and do not nag.

ForcesThe tool stays usable during the messy middle of a programme.
CostsIt will not stop a team from shipping an unratified baseline. It is a helpful tool, not a compliance regime — by choice. Every organisation we have watched adopt a compliance-regime tool ends up keeping the real work somewhere else.
B8

Automated suggestions are reporting, never a decision input

Everything the system proposes — a decomposition candidate, a rewrite, a quality flag — exists for a human to act on. One machine-generated signal is never chained into a second as though the first had already been verified.

ForcesA quality classification may inform what a human next requests. It never issues that request itself.
CostsLess automation than is technically achievable. This is deliberate: the step that is cheapest to chain automatically is the one nobody is allowed to delegate.

02 Does this replace Jira?

No, and it is designed specifically not to. This is the first question every reviewer asks, so it is answered before the diagram rather than after it.

Stays exactly where it isMoves into the requirements registry
Epics, stories, sprints, boardsThe customer’s requirements, verbatim
Assignees, workflows, velocityThe decomposition into system requirements
Test plans and executionsThe claim that an epic satisfies a requirement
Everything your teams do dailyThe traceability record and its audit artifacts

Engineering teams keep working in the tools they already use. Nobody is asked to update status in a second place — status flows from where the work happens. What the registry adds is the one artifact none of those tools holds: an authoritative, live, auditable answer to “which requirement is this work discharging, and is it covered?”

If your teams have to maintain the traceability by hand, we have built the wrong thing.

03 The workflow

Five stages. The gates that refuse are as much a part of the design as the transitions that proceed.

Why the shape is unusual in two places

The fidelity gate is separate from triage, and it comes first. Most tools import and immediately let you start editing. We lock the customer’s text and its provenance the moment a human confirms the extraction is faithful — and only then. Locking at import would freeze text nobody has checked; never locking means the baseline drifts. Immutability is the reward for review, not the consequence of upload.

“Not our requirement” is a first-class outcome. A requirement allocated to the customer’s regulator, an independent assessor, or the operator is a genuine, well-formed requirement that we are not going to discharge. It stays in the set, marked. Dropping it makes the traceability record incomplete; treating it as ours makes the estimate wrong.

254 requirements → 575 obligations. Half were somebody else’s.

In a real customer requirements document we put through this workflow, 254 numbered requirements decomposed into 575 distinct obligations — and 286 were the supplier’s while 289 were owed by nine other parties. Almost exactly half of the document was not a requirement on the product, and that split appeared nowhere in the document’s own structure.

A supplier estimating from the 254 numbered requirements — which is what estimating practice does by default — is sizing against a document where half the obligations are somebody else’s.

04 States and transitions

Four independent axes, not one status field

The single most common failure in requirements tooling is one status column carrying four unrelated meanings. We keep them apart deliberately.

AxisValuesAnswers
Lifecycleactive · archivedIs this record current? Nothing is ever deleted
Standingreceived · committed · satisfied · abandonedWhat is our posture toward this obligation?
Dispositionfindings → derived verdictIs this requirement usable as written?
Allocationthe owning partyWhose obligation is it?

Satisfaction is deliberately not on this list. It is never a stored state — it is computed at read time, every time, from live queries (B3, B4). A requirement does not “become” satisfied; it is observed to be, or the observation fails and is declared unavailable.

Disposition and allocation are independent of each other, and both are independent of standing. A requirement can be perfectly well-formed and not ours; badly formed and unmistakably ours; committed to and later found contradictory. Collapsing any two of these into one field is how a requirements baseline stops being trustworthy.

What each state means

StateMeaning
ExtractedPulled from the source document. Text is provisional — nobody has confirmed the extraction is faithful yet.
ConfirmedA human has verified the extracted text against the document. Text and provenance are now immutable. Every later step attaches around this text, never edits it.
BlockedThe statement carries no binding obligation — typically “should” rather than “shall”, or content that exists only in a diagram. It cannot be decomposed, because there is nothing to discharge. It is not a defect; it is a question for the customer.
AllocatedThe owning party is identified. This is where “ours” and “not ours” separate.
Discharged elsewhereA genuine requirement owed by another party. Retained, marked, and excluded from our estimate — but never removed from the traceability set.
DecomposedSatisfied by one or more sets of lower-level requirements. Not a leaf, and holds no direct implementation.
LeafTerminates. Holds an Implementation set and a Verification set. Epics without test plans is built-but-unverified; test plans without epics is verified-against-nothing. Neither is a satisfied requirement.
RatifiedA human has judged that the set is the right set — the Adequacy question (B6). Recorded with attribution. Never inferred, never automated.
ArchivedSuperseded or withdrawn. Preserved with all its relationships. Nothing is ever deleted.

The transitions that are not on the diagram, on purpose

Deliberate omissions

Nothing transitions to “satisfied.” Satisfaction is computed live and can move in both directions between two reads. Making it a state would make it storable, and storing it would make it wrong (B4).

Nothing transitions automatically from a machine suggestion. Every arrow with a human in the “who acts” column stays that way (B8).

There is no “approved” or “signed off” state. That is Adequacy, it is recorded as ratification with attribution, and it is deliberately not a gate that blocks the system (B7).

One known gap we would rather name than have you find

Our traceability export currently emits a row per set member, which means a requirement with no set is simply absent from the file rather than reported as uncovered. Coverage reporting has to count what is not covered, on the default view, or it is not coverage reporting. That work is specified and scheduled.

And one constraint we found the hard way

A traceability matrix over a real corpus of this size is 254 × 575 — roughly 146,000 cells. At any readable cell size that is not a view; it cannot be scanned, printed, or held in the head, no matter how correct the data in it is. The coverage ratio scales; the coverage matrix does not.

Any matrix-shaped view therefore needs a stated maximum and a defined behaviour above it — group, filter, paginate, or decline to render. Declining is legitimate, and it is the same posture as B5: better to refuse than to show something that misleads.
